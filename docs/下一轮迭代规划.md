# WorldTuner 下一轮迭代规划

日期：2026-10-16。状态：方案建议，尚未开始代码拆分、创建资源或远程部署。

## 一、目标与范围

三类前端：用户 Web、Flutter 安卓、管理 Web；两个后端：客户端 Worker、管理端 Worker；两个数据库：业务 D1、运营 D1。继续使用主仓库，独立模块、独立构建与配置；共享经过审查的类型、校验与基础工具，不复制两份业务实现。

保留当前电台、详情/播放流、地图、搜索、榜单、国家/标签/语言中英文、匿名 PV/UV 功能。用户端本轮不增加注册登录、用户画像或收藏云同步。管理端增加管理员身份验证，不等于给普通用户增加用户体系。

## 二、部署与请求边界

| 模块 | 建议部署 | 调用与职责 |
| --- | --- | --- |
| worldTuner-web | 独立 Web Worker | 保留 Next.js SSR、Server Actions、地图代理；只调用客户端 API，不绑定 D1 |
| worldTuner-mobile | Android App | HTTPS 调用客户端 Worker，API 地址仍为构建环境变量 |
| worldTuner-admin | 新的 React/Vite 管理前端模块 | 静态构建产物由管理 Worker 的 Static Assets 提供，与管理 API 同域 |
| client-worker | 独立 Worker | 公开业务读取、匿名统计上报、受控错误上报；不注册任何管理员路由 |
| admin-worker | 独立 Worker | 管理员鉴权、业务管理、统计查询、错误/审计查询、Cloudflare 日志查询代理；汇总/清理定时任务 |
| CATALOG_DB | 业务 D1 | 两个后端绑定；客户端只使用业务读取仓储，管理端使用经授权的写仓储 |
| OPERATIONS_DB | 运营 D1 | 客户端受控上报；管理端查询、汇总与清理 |

注意：这里有两个“后端 Worker”，不是整个系统只有两个 Worker。用户 Web 自身另占一个 Worker；管理前端与管理后端合并部署时，总共三个 Worker 部署单元。管理前端代码仍独立维护。若以后将管理前端放到 Pages，需要额外处理跨域及 Access 会话，因此本轮优先同域。

域名仅用示例：用户 Web 为 www.example.com，客户端 API 为 api.example.com，管理前端/API 为 admin.example.com。保留现有 `/api/...` 与 `/admin/api/...` 契约，域名与本地、预发布、生产环境分别配置，不重新写死之前移除的线上地址。

当前 Web 使用 Next.js 15、Server Actions 和 OpenNext，优先沿用现有 Worker 适配验证；不要为此次拆分顺便改前端框架。Pages 静态导出不能直接承接现有全部服务端功能。官方当前对新 Next.js 项目另有 vinext 推荐，作为后续独立评估项，不与本轮业务拆分绑定。

## 三、代码组织

优先在现有 worldTuner-api 中维护共享源码与两个独立入口，避免立即移动所有项目：

- src/entries/client.ts、admin.ts：只负责对应 HTTP 入口与定时/后台事件导出。
- src/apps/client-app.ts、admin-app.ts：各自装配路由与中间件。
- src/modules/stations、catalog、map：客户端读取业务。
- src/modules/admin：管理写入与管理员服务。
- src/modules/metrics、reports、audit：统计、错误报告和审计业务；读取与写入职责分开。
- src/auth、middleware、database、shared：鉴权、通用能力与数据库契约。
- migrations/catalog、migrations/operations：两库分别管理迁移。
- wrangler.client.jsonc、wrangler.admin.jsonc：独立名称、路由、资源绑定、Secrets 和环境。
- worldTuner-admin：单独的前端项目，只依赖管理 API 契约。

公共业务入口不得导入管理路由或创建管理服务，也不能靠一个运行时开关暴露/隐藏管理接口。共享基础设施不意味着共享 HTTP 权限。现有 SQLite 适配可保留作为本地调试与契约测试能力，Cloudflare D1 为首要部署目标。

pnpm 使用电脑已有可执行文件与本机 store，遵守根 AGENTS.md；不在项目内安装 pnpm 或创建 store。

## 四、两个数据库如何分工

### 业务库 CATALOG_DB

保留 country、language、tag、station、station_stream、station_link、station_source、station_tag、station_language、moderation_record 等业务表，保留原有字符串 ID、译名与关联。

客户端不直接访问 D1；用户 Web/安卓同样没有数据库凭据。D1 Binding 不是可配置的 SQL 只读账号，本轮“客户端只读业务表”由独立入口、仓储职责、路由注册和测试保证，不宣称平台层面已有只读授权隔离。

### 运营库 OPERATIONS_DB

- 现有 metric_daily_views、metric_daily_unique、metric_monthly_unique、metric_daily_uv、metric_monthly_mau。
- client_error_events：有限保留期、脱敏后的客户端错误样本。
- client_error_daily：按日期、平台、版本、错误指纹的汇总。
- admin_actors：Access 身份映射、应用内角色、启用状态。
- admin_audit_events：管理员操作结果、实体 ID、变更摘要、时间与 requestId。

不在运营库存完整 HTTP 请求/响应、音频内容、全部搜索词、完整播放历史、原始 IP、Token 或 Cookie。

两库共享账号级读写额度和总存储计量，不能通过拆库翻倍额度；单库容量限制分别计算。运营写入暴涨仍可能耗尽账号免费额度，所以拆库之外还要限流、聚合与清理。请求数与数据库读取行数不是一回事，后台报表也需查询汇总表并使用索引。

### 迁移原则

当前代码虽然有 METRICS_DB 类型，但默认配置仅绑定一个 DB，且存在 `METRICS_DB ?? DB` 回退，本轮应去掉生产回退，缺少运营库绑定时明确报配置错误，不能继续往业务库写统计。

先盘点实际 D1 表、迁移记录和统计数据，再拆迁移目录；不可将已经在现有库执行过的历史迁移直接重命名后再次执行。新库使用明确基线；旧库先备份，复制统计数据、核对数量与汇总后切换绑定，再决定旧表清理。开发和预发布使用独立数据库，不能共用生产绑定。

跨库写入不设计为一个数据库事务。电台修改与审计必须可靠关联：在业务库建立少量 admin_outbox 事件记录，与电台修改放在同库原子批次中提交；由管理 Worker 定时将事件幂等转入运营库审计表并标记完成。它是可靠交付的基础设施例外，不在业务库保存完整运行日志。迁移后再清理已投递事件。

## 五、日志、统计和错误报告分开处理

| 类型 | 来源 | 主要存储 | 管理端用途 |
| --- | --- | --- | --- |
| Worker 运行日志 | 后端自动生成 | Cloudflare Workers Logs | 按请求 ID、错误、路由、时间排查问题 |
| PV/UV 与增长统计 | Web/安卓固定页面事件 | 运营 D1 去重与汇总表 | 趋势、平台分布、活跃访客 |
| 客户端错误报告 | Web/安卓主动上报 | 运营 D1 样本与汇总 | 按版本/平台定位高频异常 |
| 管理员操作审计 | 服务端从已验证身份生成 | 运营 D1，业务 outbox 可靠转交 | 谁在何时修改了哪个电台及结果 |

### 运行日志

两个后端启用 Workers Logs。结构化字段建议为 timestamp、service、environment、release、requestId、route 模板、method、status、durationMs、errorCode。记录不含参数的路由模板，不输出 Authorization、Cookie、原始上报 ID 或带密钥的 URL。客户端错误提示和上报可携带服务端返回的 X-Request-Id，帮助关联。

性能排查优先结合 HTTP 总耗时、D1 查询耗时/扫描行数和缓存命中率；普通成功日志采样，异常记录按规则保留。不能假设采样日志是完整审计或精确访问计数。

首版可先提供 Cloudflare 控制台排查入口，再接入管理 Worker 的受限日志查询代理。管理端只允许查询固定的本项目 Worker、固定时间上限、条数和允许的筛选字段，不把任意 Cloudflare 查询能力暴露给浏览器。Cloudflare 查询 Token 仅存管理 Worker Secret，使用满足该查询接口的最小账号权限。

Workers Logs 有平台保留期和采样/用量约束，不承诺永久日志或在网页中实现 tail -f 的完整实时流。首版用分页/手动刷新，后续再独立评估长期日志归档和告警。

### 访问统计

延续现有轻量 PV/UV，不增加完整行为轨迹。服务器接收时间决定日期，默认 UTC；后台明确标识统计时区，不混用客户端本地日期。

- PV：固定页面标识的有效页面访问事件；定义只在进入/路由切换时计数，普通组件重绘不计数。
- UV/DAU：匿名安装/浏览器标识在日范围去重，Web 与安卓分别统计。
- MAU：月范围去重，不把每天 UV 简单相加。
- 增长：先提供日/月活跃访客趋势、PV 趋势与环比。每日 UV 不能称为“新增注册用户”；跨端不能自动识别为同一个人。需要“首次安装数”时另行审查最小去重设计，不直接增加长期跨期用户跟踪。

公开写入口必须校验字段、限流并处理网络重试。建议新增 eventId，客户端重试复用同一 ID；运营库短期幂等去重，避免网络重试虚增 PV。保持旧客户端请求兼容：缺 eventId 的旧请求仍可接收，但标明其 PV 可能重复。匿名 UUID 只在内存参与按期哈希，不直接持久化原值。

日去重先沿用 35 天、月去重保留最近两个月，汇总长期保存；事件幂等 ID 初始保留 7 天。汇总与清理支持幂等重入，按批次清理，避免一次操作大量历史行。

### 客户端错误报告

先自建轻量 report 接口，不立即引入 Sentry 等额外服务。初始事件类型：未处理异常、API 请求失败、播放初始化/播放失败、地图初始化失败。播放源失效属于业务故障，单独分类，不能全部当作 App 崩溃。

建议字段：eventId、platform、appVersion、buildNumber、eventType、errorCode、stationId（可选）、requestId（可选）、经过截断和脱敏的 message/stack。时间以服务端为准，客户端时间仅作辅助；不上传完整请求正文、用户搜索词或带 query 的音频地址。

错误指纹按归一化代码/堆栈计算，同类问题聚合次数并保留少量样本。客户端不因报告失败弹窗，不阻塞播放与页面，也不对报告失败再次上报形成递归。首版采用小队列、有限重试、批量提交；服务端限制字节数、批量条数、单来源频率，并对重复错误采样。客户端版本字段均视为不可信输入。

建议初始策略：单次最多 10 条、正文最多 16KB；同指纹短时间合并；原始脱敏样本保留 14 天，日汇总先保留 180 天。参数配置化，预发布验证后调整，不作为已实现能力。

上报是公开输入，不保证恶意请求产生的统计是真实用户行为。waitUntil 仅用于不阻塞主响应，不能当作可靠队列；首版上报接受有限丢失。后续确实需要可靠缓冲时再加 Queues，由现有管理 Worker 消费，不必增加第三个后端应用。

## 六、管理员安全

### 登录与身份

推荐 Cloudflare Access 保护整个管理域名，包括管理页面与 API。只允许明确的管理员身份，通过受支持身份提供商登录并要求 MFA。禁止仅判断某个身份请求头存在；管理 Worker 验证 Access JWT 的签名、issuer、audience、expiry，缓存 JWKS 并支持轮换。

身份验证后按稳定的 issuer + subject 映射 admin_actors，并检查 enabled 与角色；邮箱用于展示/审计，不直接信任客户端传入的管理员 ID 或角色。首位管理员通过受控配置/迁移初始化，不提供公开注册或“第一个登录者自动成为管理员”。

建议首版 owner（全部管理能力）、viewer（只读）两种角色，必要时再增加 editor。角色检查必须在服务端每个接口执行，前端隐藏按钮不是权限控制。管理员本人身份可记录在审计中，与普通访客统计分开。

现有静态 ADMIN_TOKEN 仅保留本地/隔离测试兼容；新生产管理入口不得同时开放静态 Token 绕过 Access。自动化任务后续单独定义机器身份和最小权限，不把管理员 Token 放进 Web/安卓或前端环境变量。

### 防止绕过及恶意写入

- 自定义管理域名、workers.dev、预览地址和 Service Binding 等所有入口统一走应用内鉴权；不需要的直连/预览入口关闭或同样保护。
- 管理页面/响应 no-store，不能缓存带身份的数据；公开 JSON 缓存与管理查询缓存分开。
- 浏览器管理写请求只允许同源，校验 Origin 并采用 CSRF 令牌；JSON Content-Type、方法与请求体大小均校验，GET 不执行写操作。
- 管理员独立限流，与公开搜索分开；密钥、Access audience、绑定均按环境配置。
- 业务 SQL 参数绑定，更新字段白名单，分页与日期范围上限；禁止提供“执行任意 SQL”或“输入任意数据库路径”接口。
- 每次管理写入生成审计事件；错误响应不返回堆栈、SQL、Secrets 或内部存储信息。
- 首版以软下架代替硬删除；编辑使用 revision/更新时间冲突检查，避免多人覆盖。

### 缓存一致性

当前业务修改后缓存按 TTL 更新，拆分后需明确管理写入到用户可见的延迟。首版将普通列表/字典的 TTL 控制在可接受窗口（建议不超过 60 秒），地图快照单独声明刷新窗口（初始 300 秒）；客户端文件缓存也必须尊重过期和重新校验。

管理端返回保存成功及预计生效窗口，不伪称边缘全局缓存已即时失效。紧急全局下架属于单独验收项：需要实现并验证可靠全局失效/版本策略后才能承诺即时效果，不能仅删除当前节点的缓存。

## 八、分阶段实施与验收

### P0：资源与契约盘点

确认实际 D1 数据、迁移记录、现有统计数量、域名和 Cloudflare 套餐；确定管理身份与 Access 策略。固定现有业务接口及中英文行为作为回归基线，设计两库迁移与回退。此阶段只读检查，不改生产数据。

### P1：两个后端入口与两库

现有用户业务保持兼容，抽出独立 admin Worker 与共享模块；分开 Secrets、路由、两库迁移。切换后客户端 Worker 请求管理接口必须 404；业务库不再新增统计表/行，管理接口默认未配置即拒绝。保留本地 SQLite 契约测试与 D1 预发布验收。

### P2：管理员身份与电台管理

接入 Access JWT 验证、MFA、角色和同源写保护；完成最小管理前端。先上线电台查找、详情、上下架、译名和播放地址编辑，增加冲突校验与审计 outbox。验证未登录、过期/伪造 Token、错误 audience、viewer 写入、直连入口绕过均失败。

### P3：访问分析与汇总

统计独立入运营库，升级 eventId 去重，补齐报表查询及管理前端。验证固定数据样本的 PV、日 UV、月 MAU、UTC 边界、重试幂等、历史迁移和清理重入。报表查询不得全表扫描访客标识。

### P4：错误报告与日志查询

Web/安卓接入轻量错误上报，完成去重、脱敏、保留期和管理查询；两个 Worker 使用结构化运行日志。日志读取使用最小权限服务端 Token；限流/故障不会拖垮电台 API。先完成查询，再按真实需求增加告警或长期归档。

### P5：预发布、迁移与灰度

独立 D1 与测试域名全链路验证，测请求耗时、D1 扫描/写入行数、缓存与地图快照大小。生产备份后迁移，先部署两个后端，再管理前端和用户 Web，最后安卓测试包。保留可回退的客户端 API 地址及旧服务，数据库迁移先做增量，不立即删旧表。切换前明确回退期间业务与统计是否需要补录，避免双写重复。

每阶段交付：可运行代码、相关契约/测试、迁移与回退说明，以及实际验证结果。一个阶段通过后继续下一阶段，不同时更换业务架构、Web 框架和普通用户体系。

## 九、需要在实施前确定的少量信息

1. 管理员初期是否只有你本人（本方案默认本人为 owner）。
2. 正式 Web/API/管理域名（文中仅用 example.com）。
3. 是否接受普通变更最多 60 秒、地图最多 300 秒的首版缓存窗口。
4. 日志查询的保留需求；默认先使用平台现有保留期，错误样本 14 天。

这些不阻碍先完成本地入口拆分、契约与迁移方案，但正式 Access 策略和生产发布需要真实配置。
